# Киоск-режим (Chrome Kiosk)

Запуск дашборда AI CCTV PPE Detection как отдельного полноэкранного приложения на
машине с монитором (диспетчерская/пост оператора), а не как вкладки браузера.
Используется штатный **режим киоска Chromium/Chrome** (`--kiosk`): без адресной
строки, вкладок, меню и других элементов управления браузером.

Два независимых варианта в зависимости от ОС хоста:

- **Linux** — Chromium запускается **прямо в Docker-контейнере** вместе с
  бэкендом (`docker compose --profile gpu up --build` поднимает всё сразу, без
  ручных скриптов) — см. раздел «Linux: Chromium в Docker» ниже.
- **Windows** — нативный Chrome на хосте через PowerShell-скрипты в `kiosk/`
  (Docker Desktop + WSLg для GUI-в-контейнере на практике оказался ненадёжным —
  падал на разных этапах: CRLF в entrypoint, отсутствие D-Bus, "missing X
  server" при прокидывании дисплея через WSLg). См. раздел «Windows: нативный
  Chrome» ниже.

## Linux: Chromium в Docker

Требования: Linux-хост с физическим монитором и залогиненной X11-сессией
(обычная рабочая станция или диспетчерская с автологином).

**Один раз** перед первым запуском на хосте разрешить локальным
Docker-контейнерам подключаться к X-серверу:

```bash
xhost +local:docker
```

(без этого Chromium в контейнере упадёт с "cannot open display" — сервер
проверяет, кому разрешено рисовать в X, и по умолчанию контейнеры туда не
допущены). Эту команду стоит добавить в автозапуск X-сессии (`~/.xprofile`
или автостарт DE), чтобы разрешение переживало перезагрузку.

Дальше — просто:

```bash
docker compose --profile gpu up --build     # или --profile cpu
```

Поднимаются `app-gpu`/`app-cpu` (бэкенд) и `kiosk-gpu`/`kiosk-cpu` (Chromium):
киоск-контейнер стартует после `condition: service_healthy` бэкенда, ждёт
`/health` и открывает Chromium в полноэкранном режиме на дисплее хоста.
Никаких `.ps1`/`.sh` вызывать не нужно — только `docker compose up`.

Как это работает (`docker-compose.yml`, `kiosk/Dockerfile`,
`kiosk/entrypoint.sh`):
- Контейнер монтирует `/tmp/.X11-unix` хоста и `~/.Xauthority` (для
  X11-авторизации без ослабления `xhost` до полностью открытого доступа,
  `XAUTHORITY=/root/.Xauthority` внутри контейнера).
- Профиль Chromium — в именованном volume (`kiosk_profile_cpu`/`_gpu`),
  переживает пересоздание контейнера (сессия/JWT не сбрасываются).
- Если предыдущий запуск упал (падает контейнер бэкенда, `docker compose
  restart` и т.п.), в volume могут остаться `SingletonLock`/`SingletonSocket`
  от Chromium — `entrypoint.sh` снимает их перед стартом (иначе Chromium
  решает, что профиль "повреждён" другим процессом).
- Отдельный `dbus-daemon --system` поднимается внутри контейнера — без него
  Chromium пишет "Failed to connect to the bus: ... system_bus_socket" в лог
  (не фатально, но лог засоряет).
- `--no-sandbox` — контейнеризированный Chromium без доп. capabilities не
  может поднять свой sandbox; стандартный компромисс для Docker.

Если после `xhost +local:docker` контейнер `kiosk-gpu`/`kiosk-cpu` всё равно
не рисует окно — смотрите `docker compose logs kiosk-gpu`: чаще всего либо
`xhost` не выполнен (или сброшен после перезагрузки — не персистентная
настройка X-сервера), либо на хосте вообще нет активной X-сессии (SSH без
`X11Forwarding`/headless-сервер — тогда Chromium рисовать некуда физически).

## Windows: нативный Chrome

## Что делают скрипты

| Скрипт | Назначение |
|---|---|
| `kiosk/start_docker_gpu_kiosk.ps1` | Поднимает бэкенд `docker compose --profile gpu up -d --build` (detached, не блокирует терминал) и сразу передаёт управление `start_kiosk.ps1`. Нужен, если бэкенд и киоск — одна и та же Windows-машина: **`docker compose ... up` (без `-d`) сам по себе Chrome не откроет** — терминал блокируется логами контейнера, и до киоска дело не доходит. |
| `kiosk/start_kiosk.ps1` | Открывает Chrome в режиме киоска на нужном URL. Если Chrome закрылся/упал — перезапускает автоматически (пока не поставлен стоп-флаг). Использует отдельный профиль Chrome (`%LOCALAPPDATA%\PPEKiosk\ChromeProfile`), поэтому вход в систему (JWT) не сбрасывается при перезапуске. Повторный запуск, пока уже есть работающий экземпляр, сразу завершается с предупреждением (защита от дублирующихся Chrome на одном профиле). |
| `kiosk/install_autostart.ps1` | Регистрирует задачу планировщика Windows: `start_kiosk.ps1` запускается автоматически при входе пользователя. Требует прав администратора. |
| `kiosk/uninstall_autostart.ps1` | Удаляет задачу автозапуска. |
| `kiosk/stop_kiosk.ps1` | Штатно останавливает киоск (стоп-флаг + закрытие процесса Chrome киоска), без остановки задачи автозапуска. |

## Быстрый старт (ручной запуск, проверить перед автозапуском)

```powershell
cd kiosk
.\start_kiosk.ps1                              # http://localhost:8000 — бэкенд на этой же машине
.\start_kiosk.ps1 -Url "http://192.168.0.85"   # если фронт вынесен на отдельный сервер (см. deploy.env)
```

### Бэкенд и киоск на одной GPU-машине (Docker)

Если бэкенд запускается через `docker compose --profile gpu up --build` **на той
же Windows-машине**, где стоит монитор — обычный (foreground) запуск docker
compose не откроет Chrome: терминал занят логами контейнера, а `start_kiosk.ps1`
никто не вызывает. Используйте объединённый скрипт вместо ручной пары команд:

```powershell
cd kiosk
.\start_docker_gpu_kiosk.ps1                              # docker compose up -d --build + kiosk
.\start_docker_gpu_kiosk.ps1 -NoBuild                      # без пересборки образа (если уже собран)
```

Он поднимает контейнер в фоне (`-d`), затем вызывает `start_kiosk.ps1`, который
дожидается `/health` (см. `-WaitForBackendSec`, по умолчанию 300с — сборка GPU-образа
и прогрев моделей дольше, чем дефолт `start_kiosk.ps1`) и открывает Chrome.
Для автозапуска при входе в систему укажите этот скрипт в качестве действия
задачи планировщика (см. `install_autostart.ps1` — по умолчанию он регистрирует
`start_kiosk.ps1`; для сценария «бэкенд+киоск на одной машине» отредактируйте
`-Execute`/`-Argument` под `start_docker_gpu_kiosk.ps1`, либо поднимайте бэкенд
отдельной задачей/службой, а `start_kiosk.ps1` — как обычно).

Выйти из полноэкранного режима вручную во время проверки — `Alt+F4` (Chrome
перезапустится через ~2 сек, это ожидаемо) либо `.\stop_kiosk.ps1` из другого
PowerShell (полная остановка).

## Постоянная установка (выделенный киоск-терминал)

1. **Создать отдельную локальную учётную запись Windows** для киоска (не
   администратора), например `ppekiosk`, с автоматическим входом:
   ```
   Панель управления → Учётные записи → netplwiz →
   снять галочку «Требовать ввод имени пользователя и пароля» → выбрать ppekiosk
   ```
   Либо через реестр (`HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon`):
   `AutoAdminLogon=1`, `DefaultUserName`, `DefaultPassword`, `DefaultDomainName`.
2. Убедиться, что бэкенд (`docker compose --profile gpu up -d` или
   `python app.py`) поднимается автоматически при загрузке машины —
   `start_kiosk.ps1` ждёт `/health` до `-WaitForBackendSec` (по умолчанию 120с),
   но не бесконечно.
3. Отключить экранную заставку, спящий режим и автообновления Windows с
   принудительной перезагрузкой (Групповые политики / `powercfg`) — иначе
   терминал уйдёт в сон или перезагрузится посреди смены.
4. Установить Google Chrome под учёткой `ppekiosk` (или системно).
5. Скопировать репозиторий (или хотя бы папку `kiosk/`) на терминал.
6. Из PowerShell **от имени администратора**, под учёткой `ppekiosk` (или
   указав `-User`):
   ```powershell
   cd kiosk
   .\install_autostart.ps1 -User "$env:COMPUTERNAME\ppekiosk" -Url "http://localhost:8000"
   ```
7. Перезагрузить машину — после автологина `ppekiosk` Chrome должен открыться
   в киоске автоматически.

## Как остановить / выйти (для администратора)

Уровень блокировки — только Chrome (см. ниже про более глубокую блокировку),
поэтому у администратора всегда есть штатный путь остановить киоск:

- Локально под учёткой киоска: `kiosk\stop_kiosk.ps1` — закроет Chrome и не даст
  ему перезапуститься, задача автозапуска при этом остаётся зарегистрированной
  (сработает при следующем входе).
- Полностью снять автозапуск: `kiosk\uninstall_autostart.ps1` (нужны права
  администратора).
- Экстренно: `Ctrl+Alt+Del` → «Сменить пользователя» → войти в другую
  (администраторскую) учётную запись, если она есть на машине.

## Что НЕ входит в этот уровень блокировки

Реализован только киоск-режим Chrome (флаги `--kiosk`, `--noerrdialogs`,
изолированный профиль, автоперезапуск при закрытии). Это не блокирует:
- переключение окон (`Alt+Tab`), меню «Пуск», диспетчер задач — оператор
  технически может свернуть Chrome или завершить процесс через диспетчер задач
  (правда, `start_kiosk.ps1` тут же откроет его заново, если процесс PowerShell
  ещё жив);
- сочетания клавиш Windows.

Для более глубокой блокировки ОС (запрет Alt+Tab/Win, скрытие панели задач,
запрет диспетчера задач) — штатный инструмент Windows **Assigned Access
(«Назначенный доступ» / Kiosk mode в Параметры → Учётные записи → Семья и
другие пользователи)**, либо групповые политики (`gpedit.msc`:
`Отключить диспетчер задач`, `Удалить меню «Выполнить»` и т.п.). Это отдельная
настройка ОС поверх `kiosk/`, в репозитории не автоматизирована.

## Полезные флаги Chrome, использованные в скрипте

- `--kiosk <url>` — полноэкранный режим без UI браузера.
- `--user-data-dir=<путь>` — отдельный профиль, не трогает обычный Chrome
  пользователя; сохраняет вход (JWT) между перезапусками.
- `--noerrdialogs`, `--disable-session-crashed-bubble` — не показывать диалоги
  об ошибках/восстановлении сессии (мешают киоску).
- `--autoplay-policy=no-user-gesture-required` — голосовые предупреждения
  (`/api/voice_alert_audio`, см. CLAUDE.md §2.4.1) проигрываются через
  `<audio>` без клика пользователя; без этого флага Chrome блокирует автовоспроизведение звука.
- `--disable-pinch`, `--overscroll-history-navigation=0` — не реагировать на
  жесты (если сенсорный монитор).
